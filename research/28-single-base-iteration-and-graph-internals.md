# Round 19 — 单基座迭代法：图形控件内部几何全表、`howGrow` 的真正语义，与"验证工具本身在骗你"

> 承接 Round 18。验收方的要求变成了三句话：**"可用，不要搞出这么多 vi 了，你在一个基础上改就行了"**、
> **"现在还差的很远"**、**"不要什么都问我"**。于是本轮把"每版一个 vN 文件"的二分法彻底废掉，
> 改成**单基座 + 幂等构建脚本**（一个 `build.py` → 一个 `波形图.vi`），所有实验都是"改脚本 → 重建 →
> 截真实窗口 → 看图"。这一轮真正的收获不是某个像素位置，而是三件更底层的事：
> ① 图形控件内部每个零件的**相对坐标**终于列全了；② `howGrow` 不是"缩放比例"而是"加载时是否重算 bounds"的开关；
> ③ **自研打印助手导出的 PNG 不是 1:1**——前两轮有一半判断被这个假象带偏。

---

## 1. 单基座迭代法（流程本身是结论）

| 阶段 | 做法 | 为什么 |
|---|---|---|
| 源 | `src/` = 从一次 `pylv_extract` 取出的**只读** FPHb/BDHb（标签完好） | 源固定，任何实验都能一键重跑回基线 |
| 构建 | `build.py`：读 `src/` → 一串幂等替换函数 → 写 `bundle/` | 每个改动都是一个带注释的函数，可单独开关 |
| 回写 | `pylv_rebuild(mainXml, viPath)` | 每次覆盖**同一个** `波形图.vi`，不产生 vN |
| 验证 | `helper_fp_print.vi` 渲染 PNG + `PrintWindow` 截真实面板 | 两个独立证据源，互为对照 |
| 判据 | 看渲染图 + 量白色列区间 / 网格边界 | 不看任何 `ok` 自述 |

上一轮"每版一个 vN 文件 + 二分排查"的方法在**定位拒载**时有效，但在**调布局**时是灾难：
文件一多，就分不清"这次改动到底改成功了没有"。单基座 + 幂等脚本把这件事变成了可回归的。

## 2. 坐标系混淆：这是"改了 bounds 纹丝不动"的头号原因

bundle 里同时在用三套坐标，混一次就白跑一轮：

| 层级 | 字段 | 坐标系 | 例子（波形图控件） |
|---|---|---|---|
| 控件 | `ddo/bounds` | **面板绝对坐标** | `(119, 244, 678, 1034)` → 宽 790 高 559 |
| 控件内零件 | `partsList/*/bounds` | **相对 ddo 左上角** | 绘图区 `417` = `(76, 235, 482, 734)` |
| 坐标轴 | `scaleRect` + `scaleRMin32/RMax32` | 又一套（轴线起止点的屏幕坐标缓存） | 改了不与 bounds 同步就冲突 |

前两轮把"面板绝对坐标"填进了零件的 `bounds`（例如给 X 轴写 `top=585`，而控件高只有 559），
LabVIEW 把越界值 clamp 回一个固定位置——看起来就是"改了没反应"。
**规则：控件写绝对、零件写相对，两套数字绝不交叉使用。**

## 4. `howGrow` 的真正语义：不是"缩放比例"，是"加载时要不要重算尺寸"

这是本轮最有迁移价值的一条。`howGrow` 的取值是一组位标志（实测样本）：

| 值 | 二进制 | 出现在 |
|---|---|---|
| 5 | `0b000000000101` | 我们自己手改后"能钉住"的档位 |
| 240 | `0b000000111100` | 数组/图形控件的常规零件（**会跟随缩放重算**） |
| 194 / 120 / 56 / 10 | 小值 | 各种边框/装饰件 |
| 4096 | `bit12` | 只定位 |
| 4144 | `bit12 + 0b110000` | scale（X 轴） |
| 4288 | `bit12 + 0b11000000` | scale（Y 轴） |
| 14400 / 13440 | 大值 | 多态 cosm |

**实测行为**：
- `howGrow=240` 的零件，LabVIEW **加载时会按控件当前尺寸与设计尺寸的比例重算它的 bounds**，
  于是你写进 XML 的 bounds 被覆盖 → "改了不生效"。
- 改成 `5` 之后，**bounds 立刻被采用**（左栏卡片、波形图同时变大，第一轮验证就是靠这个突破的）。
- 但**不能无脑全改**：`550` 段内所有零件一起改 5，Y 轴标签会从绘图区左侧跳到正中间——
  因为内部还有一套按 `howGrow` 位组合推出的锚定逻辑。**一次只改一个零件。**

配套的图形控件重排配方（本轮定型）：

```python
# 1) 只把要动的那个 scale 的 howGrow 改 5，让它听 bounds 的
# 2) bounds 用【相对 ddo】坐标
# 3) scaleRMin32/RMax32（轴线起止点屏幕坐标缓存）必须同步改，否则轴线长度按旧缓存画
# 4) 别碰 treeControl(420)：改不动，且是画布撑宽的唯一原因
```

## 5. 数组控件当"卡片"用：必须连铺四层，少一层就窄一截

`indArr`（数组控件）内部不是"一个元素"，而是**四层**：

```
fPDCO (ddo)                       ← 面板绝对 bounds
└── indArr (pid 8023)             ← 显示区
    └── cosm (pid 9)              ← 元素外框（393 的 391 / 581 的 579）
        └── ddo (element)         ← 元素面（385 / 573）
            └── label (pid 11)    ← 文字区（390 / 578）
```

只把"显示区 + 元素面"铺满 —— 卡片渲染宽度永远卡在**设计尺寸**（167 / 184），
因为元素外框和文字区还留在原位。四层全铺满后：

| 卡片 | 目标宽 | 铺两层 | 铺四层 |
|---|---|---|---|
| 左栏 393 | 208 | ~150 | **192** |
| 右栏 581 | 215 | ~105 | **215** |

另外两条硬结论：
- **给 `DefaultData` 写 N 个元素 ≠ 变成 N 张卡片**。写 4 个元素，LabVIEW 只渲染 1 个 + 滚动条 + 索引框。
  正确姿势是 **1 个元素 + 多行文本**，用 `\n` 拉开视觉分组，用 `'─'*30` 画组间分隔线。
- 多行文本的 `DefaultData` 格式：`"` + **4 字节大端元素数** + **4 字节大端文本长** + 正文 + `"`，
  文本走 `s.encode('gbk').decode('mac_roman')`（mojibake 管线），CDATA 里只对控制字符写 `&#xNN;`。

## 6. 静态数据进 chart：第四次封死（四种方法，四种证据）

本轮把"要在前面板里画出曲线"的最后一条路也试完了：

| # | 方法 | 结果 | 证据 |
|---|---|---|---|
| 1 | 直接改 FPHb 里 `<PlotData>` | 里面只有 `<cnt>0</cnt>`，没有可写的数据槽 | 全文 grep |
| 2 | COM `SetControlValue('05 波形显示', [(t0,dt,Y[])])` → `MakeCurValueDefault` → `SaveInstrument` | 读回正常、保存成功，**文件只多 4 字节**，重开 `<cnt>` 仍是 0 | 保存前后 `pylv_extract` 对比 |
| 3 | `pylv_extract` 的 VITS 变体块 | 53 字节 `SourceOnly` 壳，pylabview 只能 raw fallback | 反编译输出 |
| 4 | **AIXML `value="[t0,dt,[Y...]]"`**（文档 `aixml-reference.md` 明确支持 doublewaveform 的波形值语法） | 生成 VI 成功，但 FPHb 里 `<cnt>` 仍是 0、VITS 仍 53 字节 —— **value 在 AIXML→VI 这一步被丢弃** | `datagen.vi` 实验 |

**结论（可以写进规则了）**：LabVIEW 的 chart/graph **历史数据是运行时状态，不存在 VI 文件里**。
纯前面板 VI（无程序框图）天生空图。要在前面板里"看到线"，只有两条路：

- **A. Picture 控件**画折线（数据格式已解析，见 §7）；
- **B. 造一段框图**把常量数组接到 chart 端子 → 运行 → `MakeCurValueDefault` → 删图。
  B 依赖 COM VI Server，本轮该服务整场不可用（见 §9），未验证。

## 7. Picture 控件的数据格式（终于读懂了，但还没用起来）

`stdPict` 的图像不在外部文件，**就在 FPHb 的 `<DefaultData>` CDATA 里**：

```
"                              ← 起始引号
[4 字节大端 总长]
[绘图指令流]                    ← opcode(1B) + 长度(2B 大端) + payload
"                              ← 结束引号
```

实验件（4.2 MB）里解出的三个关键字段：

| 字段 | 值 | 含义 |
|---|---|---|
| `totalBounds` | 1600 × 2560 | **图的总尺寸** |
| `srcRect` | 800 × 1280 | 源矩形 |
| `zoom` | 1.0 | 缩放 |

**本轮修正了 Round 18 的一个错误结论**：那次判"Picture 离线显示不出 1:1、10 组实验全败"，
真正原因不是数据格式不通，而是 **`totalBounds`/`srcRect` 比控件大得多，只能看到左上角**。
→ 下一次重试的姿势是：**图就做成就控件大小（约 790×559），三个字段一起对齐**。
（本轮未做，因为 §9 的验证链断了，先保住布局。）

## 9. 验证工具本身在骗你：导出 PNG 不是 1:1

前两轮有一半判断被这条带偏，必须记录下来：

| 工具 | 尺寸 | 真实性 |
|---|---|---|
| `helper_fp_print` 导出 PNG | 1578 × 775 | **非等比**：内容 x≈0.82 / y≈0.96 缩放，画布被图例树撑宽 |
| `PrintWindow(hwnd, 2)` 截真窗口 | 1280 × 846 | **1:1 真像素**（面板就是 1280×800） |

后果：按导出图量"卡片只有 HTML 的一半宽"是错的；按导出图量位置会系统性偏 18%。
**从本轮起，量像素只用 `PrintWindow` 截图，导出 PNG 只用来"看整体观感"。**

另外，这个会话里 **LabVIEW 的 COM VI Server 整场不可用**：
`GetVIReference` 连 vi.lib 里的 VI 都报 `Hex 0x7 未找到文件`，`AllVIsInMemory` 报 `0x408 拒绝访问`，
重启 LabVIEW 两次无效；`LabVIEWMCP.exe --dump-schema` 也连不上 localhost gRPC。
所以 §6 的路线 B、§7 的 Picture 重试都被环境阻塞，本轮只能靠 lvai MCP + 截图推进。
